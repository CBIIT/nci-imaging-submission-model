# nci-imaging-submission-model
Home of the MDF version of the NCI Imaging Submission Model (NCIISM).

# Rules of the road
This is an abbreviated version of the [model user's manual](https://github.com/CBIIT/ctdc-model/tree/prod/data-model-owners) developed by the CTDC team.  Reading those documents is useful if you are new to managing CRDC data models.

## Repo organization
The NCIISM repo is organized in a particular way that works with the larger CRDC ecosystem, so changes to folder structure and locations are strongly discouraged.

### Folders
*.github/workflows*: This folder containst the instructions for model validation that is run prior to a pull request. \
*docs*:  Any documentation (such as release notes) about NCIISM should live here. \
*model-desc*: This is the folder containing the actual model files (in YAML format):
  - **nci_imaging_submission_model.yml**: This contains the nodes, a list of properties for each node, and the relationships between each node
  - **nci_imaging_submission_model_properties.yml**: This is a detailed description of each of the properties in the model.  CDE references, EDP references, descriptions, are all found in this file.
  - **nci_imaging_submission_model_terms.yml**: This file is largely redundant with the properties file, and contains the properteis and their CDE references.
*src*: This contains a Python script that is used to generate Submission Portal compatible data loadign sheets.  
*submissiondocs*: This countains the actual submission sheets generated by the Python scrip in *src*.  These should be identical to those found on the Data Model Navigator page for NCIISM on the Submission Portal

### Branches
**main**: This is the production branch for NCIISM.  Note that release to production is done via tagging, not by pushing to the main branch \
**develop**: This branch is intended to be the next unreleased version of the data model.
There may be other branches as well, those should all be considered works in progress and are unsuited for production use.

## Model Change Process
Simple changes to the model can be done with any text editor, just be sure to adhere to YAML format.  For more complex changes, such as building model files from scratch using a spreadsheet as the starting point, it's strongly recommedned to use the [bento-mdf Python library](https://cbiit.github.io/bento-mdf/index.html).  The bento-mdf library ensures that the model files are valid and compliant with the latest MDF spec.  The library can be installed using *pip install bento-mdf*

- Always do work in your own branch, never in **main**.  Since branches do not control the release, there are no naming conventions for branches, but use something that others can understand.
- Do not approve a pull request if the validation tests have not passed.  Approving a PR with invalid files can cause issues downstream.
- Document your changes in your pull request descriptions
- It's poor practice to approve your own pull requests without someone else reviewing the changes, unless its an emergency.  At very least, get approval from another user is the preferred route.

## Model Versioning
All models must have a version number using the X.Y.Z format (example: 2.2.0):
- The first digit is incremented when there is a MAJOR change to the model
- The second digit is incremented when there is a MINOR change to the model
- The third digit is incremented when there is a PATCH to the model.

Examples of changes and how they impact the version number (borrowed from the CTDC manual)
### Model Version change cheat sheet

| Change | Bump | Why |
|---|---|---|
| Add a new node | **MINOR** | Nothing that validated before stops validating |
| Remove a node | **MAJOR** | Orphans previously submitted records |
| Add an optional property (`Req: 'No'` or `Preferred`) | **MINOR** | Existing files still pass |
| Add a **required** property (`Req: 'Yes'`) | **MAJOR** | Existing files now fail: they lack the column |
| Remove a property (required or not) | **MAJOR** | Submitted data has nowhere to land |
| Rename a property, node, or relationship | **MAJOR** | A rename is a remove plus an add |
| Loosen `Req` (`'Yes'` to `'No'` or `Preferred`) | **MINOR** | Loosening a constraint |
| Tighten `Req` (`'No'` or `Preferred` to `'Yes'`) | **MAJOR** | Tightening a constraint |
| Change `Type`: any change, including `string` to a list, adding or changing `units`, or "fixing" it | **MAJOR** | Values cast, store, and query differently |
| `Enum:` value added | **MINOR** | Vocabulary expands; old values still valid |
| `Enum:` value removed, commented out, or respelled | **MAJOR** | Previously valid data now fails validation |
| `Type:` replaced by an `Enum:` (literal or reference) | **MAJOR**, or **MINOR** with the coverage check | Narrows from free text to a list; see §4.4 |
| `Enum:` replaced by `Type: string` | **MINOR** | Relaxes to free text |
| `Enum:` reference swapped, or moved to a later caDSR CDE version | **MAJOR**, or **MINOR** with the coverage check | A different value set, or one that may have lost values |
| Add `useNullCDE: Yes` to a property with a value list | **MINOR** | Adds null values |
| Remove `useNullCDE` from a property with a value list | **MAJOR** | Removes accepted values |
| `Term:` added, removed, or re-coded | **MINOR** | Meaning metadata; no validation effect. **MAJOR** if it redefines the property |
| Loosen a relationship multiplicity | **MINOR** | Loosening |
| Tighten a relationship multiplicity | **MAJOR** | Tightening |
| Remove a `Mul:` declaration | **MINOR** | Falls back to the `many_to_many` default, always a loosening |
| Add a `Mul:` where there was none | **MAJOR**, unless it is `many_to_many` | Narrows from the permissive default |
| Add a relationship | **MINOR** | Additive |
| Remove a relationship | **MAJOR** | Breaks graph traversal and loaded data |
| Edit `Desc`, fix a typo, add a comment, change `Tags` no system reads | **PATCH** | No effect on validation or consumers |

**The one-sentence test:** *Would a file that validated against the previous version still validate against this one, and would every consumer still work unchanged?* Two yeses and it is not a MAJOR.

# Releasing new models

Releasing new models is done via a tag, not simply by pushing to the main branch.  

1.  Make sure you have a valid version number as described above
2. Create a pull request into the `develop` branch.  Be sure to include any release notes and other documentation about the changes.
3. Once all automated test have passed on `develop`, create a pull request into `main`.  Have the PR reviewed.
4. Tag the PR with the model version number:


``` 
git tag 1.0.0
git push main 1.0.0
```
**DO NOT REUSE TAGS**  Ever.  If there's a problem, fix it in a new version

5. Be sure to merge the tag back into the `develop` branch

```
git checkout develop && git pull origin develop
git merge origin/prod
git push origin develop
```
**Be aware** that the CRDC system works off the highest version number in the tags.
